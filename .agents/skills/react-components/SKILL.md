# React-компоненты

Применяй каждое правило ниже к каждому затронутому файлу. Пользовательские фразы — skill `i18n`. Сложный публичный API — skill `react-composition`. Тесты — skill `testing-style`.

## Размещение

- В `src/components` переиспользуемые — `common/ComponentName/`, страницы — `pages/PageName/`, layout — `layouts/LayoutName/`.
- Компонент плагина — `src/plugins/<plugin-id>/ComponentName/`.
- Компонент одного владельца держи дочерней папкой внутри него; в `common` его переносит появление независимых потребителей.
- Каждый отдельный файл React-компонента с момента создания размещай в собственной папке: `ComponentName/ComponentName.tsx`; для дочернего компонента внутри владельца используй `Owner/Child/Child.tsx`. SCSS Module, тест и story держи рядом как `ComponentName.module.scss`, `ComponentName.test.tsx` и `ComponentName.stories.tsx`.
- Надстройку `Form*` через `createFormComponent` объявляй в том же файле, что исходный контрол: `FieldExpiry.tsx` экспортирует `FieldExpiry` и `FormFieldExpiry`. Тесты — в `FieldExpiry.test.tsx`, story привязки — `FormComponent` в `FieldExpiry.stories.tsx`.
- Локальные изображения храни в `images/` внутри папки компонента.
- Компонент импортируй из его файла, не через barrel `index.ts`.
- PascalCase используется только для файлов React-компонентов; соседние вспомогательные файлы (утилиты/helpers) именуй строчными именами, например `utils.ts`, `helpers.ts`, а не `Amount.utils.ts`.

## Код и API

- Пиши function components с именованными экспортами.
- Props объявляй рядом как неэкспортируемый `interface Props`; внешний код может получить тип через `React.ComponentProps<typeof ComponentName>`.
- Обёртка над Base UI расширяет props соответствующего примитива, а обёртка над нативным элементом — его HTML-атрибуты. Остальные атрибуты передавай через `...rest`.
- Валидацию форм веди через `@avinlab/react-form`: его правила, статус и ошибки являются источником истины; для таких форм используй `noValidate`, чтобы браузерная HTML constraint validation не перехватывала отправку и не подменяла библиотечную логику.
- Сложное фокусное, клавиатурное или ARIA-поведение собирай из примитивов `@base-ui/react`; простую семантику оставляй нативной.
- В React 19 передавай `ref` как обычный prop; `forwardRef` нужен только для явной совместимости.
- Собственные boolean-props называй `isX` / `hasX`, публичные колбэки — `onX`; имена DOM/Base UI props сохраняй.
- Классы объединяй через `cn` из `@/lib/cn`; условный класс передавай объектом — `{ [styles.isX]: isX }`, без логических выражений в аргументах. SCSS Module импортируй как `styles`, а импорты изображений для `src` называй с суффиксом `ImgSrc`.
- Соседние и дочерние файлы импортируй относительно, остальные файлы из `src` — через `@/`.
- Асинхронный контент имеет явные loading, error и empty states; skeleton при загрузке сохраняет структуру layout.

## Текст и доступность

- Интерактивные элементы доступны с клавиатуры и имеют доступное имя; поле формы имеет связанную подпись, подходящие `autoComplete`, `type` и `inputMode`.
- Видимый `focus-visible` и нецветовой индикатор состояния должны сохраняться.
- Ошибку невалидного поля впервые показывай после того, как пользователь изменил значение и снял с поля фокус, либо после попытки отправить форму. Попытка отправки показывает ошибки всех невалидных полей независимо от их предыдущего редактирования и фокуса.
- После первого показа ошибки этого поля обновляй её видимость при каждом изменении значения: валидное значение скрывает ошибку сразу, а последующий возврат к невалидному значению сразу показывает её снова, без ожидания потери фокуса. Этот режим действует до явного сброса формы или загрузки новых начальных значений; успешная отправка сама его не сбрасывает.
- Ошибку поля связывай с ним через `aria-describedby`. После неуспешной отправки переводи фокус на сводку ошибок или первое невалидное поле, если изменение иначе останется незаметным.
- Динамический статус объявляй через подходящий `role="status"` / `role="alert"` и не дублируй его озвучивание.
- Семантика заголовков сохраняет иерархию. Контраст — не ниже 4.5:1 для обычного текста и 3:1 для крупного.

## Стили и layout

- Основные стили пиши в SCSS Modules; Tailwind оставляй для утилитарных классов. Подключай `@use "@/styles/kit" as *;` и существующие тематические переменные.
- Цвета, отступы, типографика, радиусы и тени берутся из проектных шкал; произвольное значение требует опоры на дизайн.
- Визуальный язык держи сдержанным: градиенты, тени, скругления, отступы и сетки следуют дизайну или явной функции.
- Для зависящей от направления вёрстки используй логические CSS-свойства и `start` / `end`. Физическое направление допустимо, когда оно является частью смысла компонента.
- RTL зеркалит layout логическими CSS-свойствами. Графически отражай только направленные UI-иконки вроде «назад/вперёд»; логотипы, фотографии, числа, статусные иконки и playback controls сохраняют направление.
- Верстай mobile-first. Значимый layout проверяй на 320, 768, 1024 и 1440 px, с длинным переводом, увеличенным текстом и в LTR/RTL.
- Изображения имеют размеры или `aspect-ratio`; изображения ниже первого экрана загружаются лениво, а вероятный LCP-ресурс — приоритетно.
- `memo`, `useMemo` и `useCallback` вводи после профилирования дорогого рендера и измеряй тот же сценарий после изменения.

## Композиция и проверка

- Definition plugin-slot и доменного hook храни рядом с компонентом-владельцем в `extensionPoints.ts`, а definition полной замены компонента — в его папке в `override.ts`. Seams разных владельцев держи у своих владельцев.
- Story служит минимальной песочницей: render-функция, один `Default`, без `Meta`, `StoryObj`, `args` и ручного `title`. Добавляй реальный контекст и отладочный вывод; другая story нужна только для иного контекста или визуально значимого состояния. Привязка `Form*` — story `FormComponent` в том же файле.
